# Reservation CLI workflow

`gleiswerk layout reservations LAYOUT OPERATIONS` evaluates one explicit,
finite sequence of RoutePlan reservation requests against a validated
schema-v3 layout. It compiles the layout's Route Definitions, starts a fresh
in-memory `ReservationManager`, runs the listed operations in order, and
writes one deterministic YAML report to standard output.

The command is a local inspection and workflow aid. Its state exists only for
that command invocation. It does not persist reservations, coordinate with
another process, command devices, observe feedback or occupancy, clear
signals, or authorize a train to move.

## Operations document

`OPERATIONS` is UTF-8 YAML with exactly one top-level `operations` list. Each
entry has one of these exact forms:

```yaml
operations:
  - operation: acquire
    owner: dispatcher-a
    route: direct-arrival
  - operation: release
    owner: dispatcher-a
    reservation: reservation-1
```

An `acquire` names an opaque nonempty `owner` and a Route Definition in the
loaded layout. A `release` names the same owner and the opaque reservation ID
returned by a previous acquisition. IDs are generated by the fresh manager;
they are not route names and should not be invented for a real integration.

Unknown routes, malformed YAML, and entries outside this small schema are
input errors: the command writes a diagnostic to standard error and exits one.
The layout is also validated and its routes compiled before any operation is
evaluated.

## Example

The checked-in examples exercise compatible acquisition and release:

```console
gleiswerk layout reservations \
  tests/fixtures/schema_v3/valid-station.yaml \
  tests/fixtures/reservation_operations/compatible.yaml
```

They acquire the independent `depot-only` and
`west-to-east-via-platform-1` plans, then release both. The report contains
one entry for every request and ends with no held reservations:

```yaml
operations:
  - operation: acquire
    owner: dispatcher-a
    route: depot-only
    success: true
    outcome: acquired
    reservation: reservation-1
held-reservations: []
```

`tests/fixtures/reservation_operations/denied.yaml` with `valid-direct.yaml`
first acquires `direct-arrival`, then attempts `within-platform`. The second
request is rejected because both routes claim `track-section:platform`:

```yaml
operation: acquire
owner: dispatcher-b
route: within-platform
success: false
outcome: incompatible
denial:
  kind: incompatible
  claim-conflicts:
    - resource: track-section:platform
      requested-provenance: [track-section:platform]
      held-reservation: reservation-1
      held-provenance: [track-section:platform]
  device-constraint-conflicts: []
```

The report always contains `topology-revision`, ordered operation results, and
the final `held-reservations` snapshot. A held reservation lists its opaque ID,
owner, route, claims, and declared Control Device requirements. Every result
has `success` and `outcome`; denied acquisitions include the complete core
denial explanation, and denied releases include `not-found` or `not-owner`.
All lists retain the deterministic ordering supplied by the reservation core.

This report explains only the declared plans and the in-memory sequence. Even
an `acquired` result is neither evidence that a device moved nor permission for
a train to move.
